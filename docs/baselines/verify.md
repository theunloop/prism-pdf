# M18 `prismpdf-verify` — base-PDF cross-validation baseline

Recorded baseline of Prism PDF's authored output graded by the independent-validator **panel**
(`crates/pdf/tests/verify_base.rs`). This is the base-PDF counterpart to the PDF/A
conformance harness (`conformance_corpus.rs`, oracle = veraPDF): veraPDF does not validate plain
PDF, so here the oracle is the *agreement of independent consumers*.

Re-run with `cargo test -p prismpdf --test verify_base -- --nocapture` (writes `target/verify-baseline.json`).

## Panel (this run)

`qpdf --check` · `mutool info` · `gs` (nullpage) · `pdfinfo` (poppler) · `pdfcpu validate` — all five
resolved. Missing tools are skipped; the harness still runs with whatever is present.

The `authored-matrix` set is generated by the harness itself from the producer. The **1.4** group
(7 files) is the M19 Phase A base feature cluster: a plain page, Separation, ICCBased, Indexed, Lab,
a reusable form XObject, and an inline image. **1.5** = `save_compact` (xref stream), **1.6** =
AES-128. The **2.0** group is the M19 Phase C + M21 structure cluster: AES-256 (cipher), Document
Parts §14.12, structure namespaces §14.7.4, UTF-8 strings §7.9.2.2, page-level `/AF` §14.13.4,
struct-element `/AF` §14.13.6, annotation `/AF` §14.13.9 and XObject `/AF` §14.13.7 (M21).

The `prismpdf-pdfa` rows grew with the part-1 (PDF 1.4) and part-4 (PDF 2.0) flavours; the pdfcpu
misses in the 2.0 rows are the DParts limitation described below, not invalidity.

The `valid` 1.7 row grew from 4 files to 8 on 2026-08-21: `lzw-content`, `ascii-chain-content`,
`runlength-image` and `ccitt-image` were added to the corpus so the seeded `document` fuzz target
reaches the decoders behind `LZWDecode`, `ASCII85Decode`, `RunLengthDecode` and `CCITTFaxDecode`
(§7.4). All four are unanimously panel-accepted, which is the point of adding them here rather than
only to the fuzzer: a seed the panel rejects is a seed that proves nothing.

> **`/ID` (§7.5.5, 2026-08).** Every authored 2.0 file in this run carries the trailer `/ID` that
> ISO 32000-2 Table 15 requires — it was silently absent before, and the panel does not catch it
> (none of the five tools enforces the 2.0 `/ID` rule; qpdf only warns about it for encrypted
> files). That is a reminder of what this oracle *is*: agreement among real consumers, not a
> conformance checker. Required-key rules like this one need the engine's own checks — here the
> writer simply always emits `/ID` from 2.0 on.

## Findings

1. **The producer emits clean output across PDF 1.4 → 2.0, and 2.0 now exercises real 2.0
   *structure*.** Every authored file is accepted by the panel majority; the 1.4–1.7 and all but the
   DParts 2.0 file are unanimous (5/5). Crucially the 2.0 group is no longer just "AES-256 over a 1.4
   document": M19 Phase C added Document Parts §14.12, structure namespaces §14.7.4, UTF-8 strings
   §7.9.2.2, and a page-level `/AF` §14.13.4 — genuine 2.0 constructs, each auto-stamped to `%PDF-2.0`
   by `min_version` and each panel-validated (the namespaces/UTF-8/page-`/AF` files are unanimous
   **including pdfcpu**). This is what moved 2.0's *Implementato* and *Validato* to `[x]`: the column
   is now backed by feature breadth, not just version stamping. (Earlier baseline: 2.0 was AES-256
   only, so *Validato* sat at `[~]` — coverage, not just existence, is now demonstrated.)
2. **Zero version-boundary violations.** The engine's own `Document::min_pdf_version` (M18 Phase 2,
   sharing the producer's feature→version table) confirms every file declares a header ≥ what its
   content requires — including the cipher floors (AES-128 → 1.6, AES-256 → 2.0).
3. **All committed should-pass corpus stays accepted** (valid + edge + the PDF/A corpus): unanimous
   on every 1.4–1.7 file, and 4/5 on the two 2.0 DParts files (pdfcpu only — see the note below).
4. **The panel is strong at confirming validity, weak at rejecting malformation.** 4 of 5 malformed
   files are accepted by the rendering-oriented tools (gs, mutool, pdfcpu all recover; poppler/qpdf
   flag only the broken/absent-`startxref` ones). Expected — real consumers do recovery, like
   Prism PDF's own reader. **Implication:** this oracle is the right instrument for *"is our authored
   output valid"*, but it is **not** a malformation detector; rejecting bad input stays the fuzz /
   anti-DoS suite's job (M10), so `malformed` is reported but **not** asserted.

## Note: a tool limitation is not invalidity (M19 Phase C, DParts)

The `authored-dparts-2.0.pdf` sample (Document Parts, §14.12) is accepted by **4 of 5** validators;
**pdfcpu rejects it with "DPartRoot not supported"** — its own message says it ships only *basic*
PDF 2.0 support. That is a tool gap, not an invalid file (qpdf/mutool/gs/poppler all accept it). It
is exactly why the gate uses **majority**, not unanimity: a valid file must not be failed because one
panel member lacks a feature. The report shows it as non-unanimous; the gate passes.

## Gate (Phase 4)

`verify_base` asserts: (1) every should-pass file is accepted by the panel majority, and (2) there
are no version-boundary violations. The `malformed` set is informational only. CI runs it in the
`verify` job (installs the panel, generates the corpus, runs the test); locally,
`PRISMPDF_VERIFY_REPORT_ONLY=1` disables the assertions for exploration.
